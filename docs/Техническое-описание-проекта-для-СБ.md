# Техническое описание проекта и архитектура
## Портал ЕЦОФ (интеграция с 1С:УХ)

**Назначение документа:** изучение используемых технологий службой безопасности  
**Версия:** 1.1  
**Дата:** февраль 2026

---

## 1. Общее описание проекта

**Портал ЕЦОФ** — веб-приложение для работы с учётными документами и интеграции с информационной системой 1С:Управление холдингом (1С:УХ). Пользователи (бухгалтеры, сотрудники организаций) работают через браузер: создают и редактируют документы, формируют пакеты, отправляют их в 1С для проведения. Данные хранятся в собственной базе данных портала и синхронизируются с 1С по протоколу HTTP.

**Зачем нужен проект:** дать единую точку входа для работы с учётными документами холдинга, снизить нагрузку на 1С, ускорить ввод данных и контроль согласований. Портал выступает промежуточным звеном между пользователями и учётной системой 1С:УХ.

**Тип приложения:** Full-stack веб-приложение (клиент–сервер).  
**Модель развёртывания:** Backend (API) и Frontend (SPA) могут размещаться на одном или разных серверах; база данных — отдельный сервис.

### 2.2. Backend (серверная часть) — технологии по назначению

**Node.js**  
*Для чего:* среда выполнения JavaScript на стороне сервера.  
*Зачем:* единый язык (JavaScript/TypeScript) для backend и frontend, богатая экосистема библиотек (npm), асинхронная модель ввода-вывода для эффективной обработки запросов и работы с БД и внешними API.

**Express**  
*Для чего:* веб-фреймворк для Node.js.  
*Зачем:* маршрутизация HTTP-запросов (GET, POST, PUT, DELETE), подключение промежуточного ПО (авторизация, валидация, логирование), раздача JSON-ответов, интеграция с middleware для CORS, загрузки файлов и т.д. Фактический стандарт для Node.js API.

**TypeScript**  
*Для чего:* типизированная надстройка над JavaScript с проверкой типов на этапе компиляции.  
*Зачем:* снижение ошибок в рантайме, лучшая поддержка в редакторах (автодополнение, рефакторинг), явные контракты для структур данных. Компилируется в обычный JavaScript перед запуском.

**PostgreSQL (библиотека `pg`)**  
*Для чего:* драйвер для подключения приложения к СУБД PostgreSQL.  
*Зачем:* выполнение SQL-запросов, пулинг соединений, поддержка транзакций и параметризованных запросов (защита от SQL-инъекций).

**MSSQL (библиотека `mssql`)**  
*Для чего:* драйвер для подключения к Microsoft SQL Server.  
*Зачем:* опциональное прямое подключение к базе данных 1С (MS SQL) для диагностики, выборочных отчётов или интеграционных сценариев. В основном сценарии интеграция идёт через HTTP API 1С.

**bcryptjs**  
*Для чего:* хеширование паролей с «солью».  
*Зачем:* пароли не хранятся в открытом виде. При входе сравнивается хеш введённого пароля с хешем в БД. Алгоритм bcrypt устойчив к перебору и rainbow-таблицам.

**jsonwebtoken (JWT)**  
*Для чего:* создание и проверка подписанных токенов аутентификации.  
*Зачем:* после входа пользователь получает токен; при последующих запросах токен передаётся в заголовке, Backend проверяет подпись и срок действия без обращения к БД на каждый запрос. Статус сессии хранится в самом токене.

**zod**  
*Для чего:* библиотека валидации и парсинга данных по схемам.  
*Зачем:* проверка тела и параметров запросов (формат, обязательные поля, типы), возврат понятных сообщений об ошибках. Снижает риск некорректных или вредоносных входных данных.

**cors**  
*Для чего:* middleware для настройки политики Cross-Origin Resource Sharing.  
*Зачем:* браузер разрешает запросы с одного домена (например, фронтенд) на другой (API) только при явном разрешении со стороны сервера. CORS защищает от несанкционированных межсайтовых запросов и позволяет настроить белый список разрешённых доменов.

**multer**  
*Для чего:* middleware для обработки multipart/form-data (загрузка файлов).  
*Зачем:* приём загруженных пользователем файлов (скан-копии документов, приложения), сохранение на диск или в облако, ограничение размера и количества файлов.

**undici**  
*Для чего:* HTTP/HTTPS клиент для Node.js.  
*Зачем:* отправка запросов к внешним API 1С (документы, НСИ, статусы). Используется вместо встроенного `http`/`https` для лучшей производительности и поддержки современных возможностей (HTTP/2 и др.).

**dotenv**  
*Для чего:* загрузка переменных окружения из файла `.env`.  
*Зачем:* хранение конфиденциальных настроек (пароли БД, JWT-секрет, учётные данные 1С) вне кода. Файл `.env` не коммитится в репозиторий.

### 2.3. Frontend (клиентская часть) — технологии по назначению

**React**  
*Для чего:* библиотека для построения пользовательского интерфейса на основе компонентов.  
*Зачем:* декларативное описание UI, автоматическое обновление при изменении данных, переиспользование компонентов, большая экосистема и документация.

**React DOM**  
*Для чего:* рендеринг React-компонентов в браузерную DOM.  
*Зачем:* связь между виртуальным деревом React и реальным HTML. Используется при вызове `createRoot`/`render` для монтирования приложения в `index.html`.

**React Router**  
*Для чего:* маршрутизация на стороне клиента (SPA).  
*Зачем:* отображение разных «страниц» (компонентов) по URL без перезагрузки браузера, поддержка вложенных маршрутов, защищённые маршруты (например, требующие авторизации).

**Vite**  
*Для чего:* сборщик и dev-сервер для современных веб-приложений.  
*Зачем:* быстрая сборка и горячая перезагрузка в разработке, оптимизация бандла в production (минификация, code splitting), нативная поддержка ES-модулей и TypeScript.

**Ant Design**  
*Для чего:* UI-библиотека с готовыми компонентами.  
*Зачем:* таблицы, формы, кнопки, модальные окна, навигация, календари и т.д. Единый дизайн и доступность (a11y) без разработки компонентов с нуля.

**dayjs**  
*Для чего:* библиотека работы с датами и временем.  
*Зачем:* парсинг, форматирование и валидация дат при отображении документов, фильтрах и в формах. Небольшая альтернатива Moment.js.

**TypeScript**  
*Для чего:* типизация исходного кода на клиенте.  
*Зачем:* те же преимущества, что и на backend: меньше ошибок, лучше поддержка в IDE, явные типы для данных API и пропсов компонентов.

### 2.4. База данных — назначение

**PostgreSQL**  
*Для чего:* реляционная СУБД для хранения всех данных портала.  
*Зачем:* надёжное хранение, транзакции, индексы, JSON-поля для гибких структур. Хранит:
- *Пользователи и роли* — для аутентификации и авторизации.
- *Документы и версии* — учётные документы и история изменений.
- *Пакеты документов* — группы документов для отправки в 1С.
- *НСИ (справочники)* — организации, контрагенты, договоры, склады, счета, номенклатура (копия из 1С для быстрого доступа).
- *Очереди интеграции* — задачи на отправку в 1С, статусы и повторные попытки.
- *Объекты учёта и подписки* — карточки объектов, подписки организаций.

---

### 2.5. Интеграции — назначение

**1С:Управление холдингом (1С:УХ)**  
*Для чего:* учётная система, куда отправляются документы и откуда получаются справочники.  
*Зачем:* проведение документов, контроль статусов, актуальные НСИ. Обмен по HTTP(S), по протоколам, реализованным в HTTP-сервисах 1С.

**Прямое подключение к БД 1С (MS SQL Server)**  
*Для чего:* опциональный доступ к базе 1С напрямую (без HTTP API).  
*Зачем:* диагностика, специальные отчёты, интеграционные сценарии, где HTTP API недоступен или недостаточен. В основном используется HTTP API.

## 3. Архитектура системы (подробно)

### 3.1. Логическая схема

```
[Пользователь] → [Браузер] → [Frontend (SPA)] → [Backend API] → [PostgreSQL]
                                     ↓                    ↓
                                     └────────────────→ [1С УХ (HTTP API)]
```

### 3.2. Назначение каждого блока

**Пользователь**  
*Для чего:* конечный пользователь системы (бухгалтер, сотрудник организации, администратор).  
*Зачем:* работает через веб-браузер, вводит данные, просматривает документы и отчёты.

**Браузер**  
*Для чего:* клиентское окружение (Chrome, Firefox, Edge, Safari и др.).  
*Зачем:* выполняет JavaScript-код фронтенда, отображает интерфейс, отправляет запросы к Backend API.

**Frontend (SPA)**  
*Для чего:* одностраничное приложение (Single Page Application) — набор статических файлов (HTML, JS, CSS).  
*Зачем:* весь интерфейс загружается один раз; переходы между «страницами» без перезагрузки; запросы к API в фоне; быстрый отклик и удобство работы.

**Backend API**  
*Для чего:* серверная часть приложения, принимает HTTP-запросы от Frontend.  
*Зачем:* выполняет бизнес-логику, обращается к БД и внешним системам, проверяет права, валидирует данные, возвращает JSON. Единственная точка входа для работы с данными.

**PostgreSQL**  
*Для чего:* основная база данных портала.  
*Зачем:* надёжное хранение документов, пользователей, справочников, очередей; транзакции и целостность данных.

**1С УХ (HTTP API)**  
*Для чего:* внешняя учётная система холдинга.  
*Зачем:* проведение документов, выгрузка НСИ, проверка статусов. Интеграция только через публичные HTTP-сервисы 1С.

### 3.3. Основные модули Backend — назначение

| Модуль | Для чего | Зачем |
|--------|----------|-------|
| **auth** | Вход, регистрация, выдача JWT | Идентификация пользователей, защита API |
| **documents** | CRUD документов, версии, статусы, файлы | Работа с учётными документами |
| **packages** | Формирование пакетов, отправка в очередь | Групповая отправка документов в 1С |
| **files** | Загрузка, скачивание, удаление файлов | Прикрепление скан-копий и приложений |
| **nsi** | Предоставление справочников | Подстановки в формах (контрагенты, склады и т.д.) |
| **admin** | Пользователи, организации, логи, очередь | Администрирование и мониторинг |
| **uh-db** | Проверка подключения к 1С | Диагностика интеграции |
| **analytics** | Типы и значения аналитик, подписки | Работа с субконто и MDM |
| **organization** | Данные организации, сотрудники | Управление организацией |
| **objects** | Карточки объектов, подписки | Объекты учёта и их распределение |

**Сервисы (фоновые процессы):**  
Очередь УХ — асинхронная отправка документов; синхронизация НСИ — выгрузка справочников из 1С; webhooks — доставка событий в дочерние системы.

### 3.4. Основные модули Frontend — назначение

| Модуль | Для чего | Зачем |
|--------|----------|-------|
| **Страницы** | Логин, документы, пакеты, НСИ, объекты, админка | Полный функционал интерфейса |
| **API-клиент** | Единый слой запросов к Backend | JWT в заголовках, обработка ошибок |
| **Контексты** | Текущий пользователь, права | Авторизация и проверка доступа |

## 4. Безопасность и аутентификация (подробно)

### 4.1. Аутентификация — назначение

**JWT (JSON Web Token)**  
*Для чего:* токен с подписью, содержащий идентификатор пользователя и срок действия.  
*Зачем:* после входа пользователь получает токен; клиент передаёт его в заголовке `Authorization: Bearer <token>`; Backend проверяет подпись и срок без запроса к БД на каждый запрос. Снижает нагрузку и упрощает масштабирование.

**bcrypt**  
*Для чего:* одностороннее хеширование паролей с солью.  
*Зачем:* пароли не хранятся в открытом виде; при утечке БД пароли не восстанавливаются. Алгоритм устойчив к перебору.

### 4.2. Авторизация — назначение

*Для чего:* проверка прав доступа к операциям и данным.  
*Зачем:* роли (ecof_admin, ecof_user, company_user и др.) определяют, какие действия доступны пользователю. Проверка выполняется на Backend при каждом запросе к защищённым ресурсам.

### 4.3. CORS — назначение

*Для чего:* настройка списка разрешённых доменов для запросов к API.  
*Зачем:* браузер блокирует запросы с других доменов, если сервер явно не разрешил их. CORS предотвращает несанкционированные межсайтовые запросы и задаёт белый список (например, только домен фронтенда).

### 4.4. Конфиденциальные данные — назначение

*Для чего:* хранение секретов вне кода (файл `.env`, переменные окружения).  
*Зачем:* пароли БД, JWT-секрет, учётные данные 1С не попадают в репозиторий. Рекомендуется HTTPS при развёртывании для защиты трафика.

## 5. Хранение и передача данных (подробно)

### 5.1. База данных — назначение

*Для чего:* PostgreSQL хранит все основные данные портала.  
*Зачем:* документы, версии, пользователи, справочники, очереди. Миграции схемы в `backend/db/migrations/` применяются при запуске Backend. Подключение задаётся переменными `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`.

### 5.2. Файлы — назначение

*Для чего:* загрузка скан-копий и приложений к документам.  
*Зачем:* хранение на диске или в настроенном хранилище. Путь — `UPLOAD_DIR`, ограничения размера — `MAX_FILE_SIZE`, количества — `MAX_FILES_PER_REQUEST`.

### 5.3. Обмен с 1С УХ — назначение

*Для чего:* передача документов и получение справочников по HTTP(S).  
*Зачем:* проведение документов в 1С, актуальная НСИ. Используются учётные данные 1С (`UH_API_USER`, `UH_API_PASSWORD`), при самоподписанных сертификатах — `UH_API_INSECURE`.
